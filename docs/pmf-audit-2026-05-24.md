## 2. TTFV Audit — 9/10

### 初回ファネル
| step | 操作 | コスト | 出典 |
|------|------|--------|------|
| 1 | `gh extension install HikaruEgashira/gh-verify` | install | README.md:46 |
| 2 | `gh verify pr 6933 --repo expressjs/express` | 1 コマンドで本物の findings | README.md:49 |

TTFV ≈ install + 1 コマンド。**他人の有名 repo(expressjs/express)をデモに借りている** → 自分の repo を晒さず即試せる(README.md:48-49)。

### 推測の ladder (resolve_repo, main.rs:840-859)
明示 `--repo`(:841-843) > 環境 `GH_REPO`(:844, `cfg.repo`) > 文脈 `detect_repo_from_git_remote()`(:845, :861)。最下段が `git remote get-url origin` から repo を推測 → repo 内なら `gh verify pr 42` だけで動く(README.md:60-61)。**ladder の底が日常利用に据えられている → 強い。**

### 失敗パス(本体)
- main.rs:843 `"--repo value cannot be empty. Use OWNER/REPO format"` — [現象]+[次の手]
- main.rs:849 `"could not resolve repo. Use --repo OWNER/REPO or set GH_REPO env var"` — [現象]+[次の手2択]
- main.rs:854 `"invalid repo format '{}'. Expected OWNER/REPO (e.g. cli/cli)"` — [現象]+[次の手]+**実例**
- main.rs:834 `"repository '{}' not found or not accessible. Check the name and your permissions"`
- main.rs:830 `"failed to run 'gh api'. Ensure the GitHub CLI (gh) is installed and authenticated"`

全エラーが `[現象]+[次の手](+実例)` の型。失敗を1リトライに変換 → 強い。

### 借りる設計
- install: `gh extension`(既存 gh エコシステムに寄生, README.md:46)
- 文脈: `git remote`(自前 repo 検出を git に委譲, main.rs:861-876)
- 出力: SARIF/JSON で GitHub Code Scanning・`gh verify fmt` パイプに接続(README.md:88-91)

### 摩擦と提案
| Severity | 摩擦 | 位置 | 提案(削る/借りる) |
|----------|------|------|----------------------|
| Low | install が `gh extension`(ゼロ install ではない) | README.md:46 | parsentry の `npx skills add` 級のゼロ install には届かない。gh 前提ユーザーには非問題なので減点は -1 のみ |
| Low | policy 選択マトリクス(README.md:127-141)が初見に多い | README.md:127 | 初回は `--audit`(policy 不要)を強く推す導線があり緩和済み(README.md:131) |

**減点理由**: ルーブリック 10 行「install すら実質ゼロ」を満たさない(gh extension 必須)。それ以外の 4 条件は全充足 → 9。

## 3. Trust Audit — 10/10

### verdict モデル(嘘をつかない設計)
`ControlStatus { Satisfied, Violated, Indeterminate, NotApplicable }`(libverify control.rs:178-183, snake_case serialize :186-192)。
- `Indeterminate`(:181, ctor :241-254 は `evidence_gaps` を保持)= 証拠不足を正直に表明
- `NotApplicable`(:182)= 対象外を明示
- binary を強制せず4値 → **嘘をつかない設計**。libverify README.md:20-22 が4値を engine の中核と明記。

### 判定と gate の分離
verdict(4値, control.rs)とは別レイヤで `GateDecision { Pass, Review, Fail }`(profile.rs:48-51)が gate 判断を担い、`Profile::map()`(profile.rs:86)が写像。**判定と gate が別レイヤ** → ユーザーが policy で厳しさを調整可能(default/oss/aiops…, README.md:178-191)。

### rollout 勾配(audit-first)
- `--audit`: 「Report results without failing on violations (always exit 0)」(main.rs:49-51)
- exit 抑制が全パスに一貫実装: main.rs:215(batch), :240, :321(matrix), :347, :406-408(`if !opts.audit { exit_if_assessment_fails }`)
- Adoption Path: Evaluate(`--audit`)→ Tune(`--policy`/`--exclude`)→ Enforce(`--audit` 外す)→ Scale(README.md:36-40)
- Action 側も `audit != 'true'` のとき初めて `exit 1`(action.yml:280-283)

信頼を稼いでから gate に移る勾配が CLI・Action 両方で明示 → 強い。

### suppression(誤検知の局所的出口)
- `--exclude <controls>`(main.rs:40-42, 実装 apply_exclusions :731-761)— 個別 control を局所抑制
- `--only <controls>`(main.rs:43-45, `conflicts_with = "exclude"` で排他、apply_only_filter :763-790)
- `--policy oss` 等で緩和(unsigned/self-review を fail→review に写像, README.md:182)
- **unknown ID は警告のみで継続**(main.rs:746-751, :774-780)— typo がツール全放棄に直結しない
- solo/monorepo 向けの具体的 exclude レシピを README が提供(README.md:129-144)

誤検知を全体放棄でなく局所抑制に変換 → 強い。

### FP feedback loop
- `benchmarks/`: 70 cases(`benchmarks/cases/`)、accuracy/precision/recall/macro-F1 を算出(benchmarks/README.md:69-80)
- 複数 policy 横断比較 `--algorithm default,slsa-l1,oss`(benchmarks/README.md:19-25)
- OSS Insight でトレンド repo を動的発見 → 実 PR で検証 → cases に curate(benchmarks/README.md:28-51)
- `fp-reduction-loop` skill(harness 内)が FP=0 まで TP/FP 分類 → policy/adapter/control 層修正の自律ループを実装

計測・分類・修正の機構が揃う → potency を継続改善できる。

### 信頼リスクと提案
| Severity | リスク | 位置 | 提案 |
|----------|--------|------|------|
| Low | benchmark の継続採点は `scoped-change` 1 control が主対象(他 control の F1 は未常設) | benchmarks/README.md:55 | 他 control にも回帰 case を拡張すると FP loop の網羅が上がる。現状でも loop 機構自体は存在し、ルーブリック 10 を満たす |

**満点理由**: ルーブリック 10 行「中間 verdict + audit-first + 局所 suppression + FP feedback loop + 判定/gate 分離」を**全て**コードで充足。

## 4. Wedge Audit — 9/10

### 楔の鋭さ
楔 = 「GitHub の PR/release/repo の SDLC 健全性を gh CLI 1 コマンドで検査」(README.md:16-18)。単一 platform(GitHub)・単一入口(gh extension)・明確な1動詞(`verify`)・3 名詞(pr/release/repo, main.rs Commands)。曖昧な「何でも監査」ではなく鋭い。

### engine / shell 分離(分離図)
```
libverify (engine, 別 repo)            gh-verify (shell, 本 repo)
─────────────────────────────         ─────────────────────────────
libverify-core   : 34 controls,        crates/cli : 薄い GitHub shell
  4値 verdict, SLSA/SOC2 mapping          - resolve_repo (main.rs:840)
libverify-policy : OPA/Rego presets       - gh api / git remote 呼び出し
libverify-output : SARIF/JSON             - engine を consume するだけ
libverify-github : GitHub adapter
libverify-verif  : Creusot 形式証明
  → "libghostty for SDLC"(README:17)
```
深さ(34 controls・形式証明・policy engine)は engine に隔離、楔は薄い(libverify README.md:16-18, 62-69)。**教科書的な libghostty パターン。** 別 platform shell(gitlab crate が既に存在: libverify crates/gitlab)を後付けできる拡張性も確保。

### 寄生先
- `gh` 拡張として寄生(README.md:46)→ gh ユーザーは新ツール習得不要
- `action.yml`(composite action)で GitHub Actions に寄生(action.yml:78-79)
- SARIF 出力で GitHub Code Scanning に寄生(action.yml:274-278)
- `gh verify fmt` でパイプライン合成に寄生(README.md:90, main.rs:124)

既存習慣に乗っている → 採用摩擦が低い。

### 10x の一点
README が掲げる差別化 = 「branch protection を超える検査」(stale review/commit signing/PR quality, README.md:27-33)。Scorecard との補完表(README.md:208-221)で「PR/release レベル compliance」を 10x ポイントに据える。ただし 34 controls × 11 policy preset(README.md:178-191)へ手が広がっており、**最初の鋭い1点**が「stale review 検出」なのか「SLSA/SOC2 compliance」なのか「PR quality」なのか、初見にはやや拡散して見える。

### scope リスクと提案
| Severity | リスク | 位置/構成 | 提案(絞る/分離する/寄生する) |
|----------|--------|-----------|--------------------------------|
| Medium | 11 policy preset + 34 control で「10x の一点」が拡散 | README.md:127-191 | README 冒頭の hero を単一ユースケース(例: 「stale review を catch する」)に絞り、compliance マトリクスは下層へ。engine の網羅性は維持しつつ楔の表面メッセージだけ鋭くする |
| Low | AI-ops controls(agent execution 検証)が SDLC 楔と別ベクトル | libverify README.md:117-126 | 将来的に別 shell(例: `agent-verify`)へ分離すると両楔が各々鋭くなる。engine 共有なので分離コストは低い |

**減点理由**: ルーブリック 10 行「明確な 10x の一点」がやや弱い(機能網羅が表面に出る)。engine 分離・寄生・鋭い入口の 3 条件は満たすため 9。

## 5. 合成と launch 判定

```
PMF readiness = (TTFV^1 · Trust^2 · Wedge^2)^(1/5)
              = (9 · 100 · 81)^(1/5)
              = 72900^(1/5)
              = 9.39 / 10
```

積モデルで最弱次元が引き下げる構造だが、本 repo は**最弱でも 9**。3 次元すべてが 8-10 帯に収まる稀なケース。

### 一言判定: **launch 可。楔は鋭く engine 分離も信頼設計も教科書的。**

優先改善(最弱次元の Medium を最上段に):
1. **[Medium / Wedge]** README hero の「10x の一点」を単一ユースケースに絞る(削る方向)。compliance マトリクスは engine の深さとして下層へ退避。
2. **[Low / TTFV]** ゼロ install は gh 前提では非問題。現状維持で良い。
3. **[Low / Trust]** benchmark 回帰を `scoped-change` 以外の control にも拡張し FP loop の網羅を上げる。
